# 怎么写一份让人看得懂的报告

这份文件是 SKILL.md「怎么写才通俗易懂」的展开：三种报告的完整模板、两个完整例子、以及常见的写坏的方式。

## 先想清楚三件事再动笔

1. **读者此刻的问题是什么？** 计划：「你要动什么、我需要拍板什么」；结果：「成了没、还剩什么」；解释：「到底怎么回事、我该怎么办」。每一个小节标题都应该是读者的问题，而不是你的工作项（「## 为什么登录会掉」好过「## 问题分析」）。
2. **哪一个机制最值得画出来？** 一份报告通常只需要一张图，画读者最难靠文字想象的那件事：数据怎么流、哪一步出错、改前改后差在哪条边上。
3. **最重要的「但是」是什么？** 没做的、没验证的、不确定的。它要出现在 tldr 里，并且单独有一个 `callout warn`。

## 两个完整例子

例子是用来对齐**形状和深度**的：开头多短、一节讲多少、图画到什么程度。你报告里的每一个数字、每一个结论都必须来自你对手头代码和数据的分析，和例子撞题也不能照搬例子的说法。

## 完整例子一：结果汇报

```markdown
---
title: 登录超时 bug 修复汇报
kind: result
subtitle: 用户登录 1 小时后被莫名踢出的问题
---

```tldr
问题修好了：登录状态会在 **1 小时**后失效，是因为前后端对 [[token|服务器发给浏览器的一张「通行证」，带着它请求就不用再输密码]] 过期时间的时区理解不一样，差了 5 小时。改了 2 个文件，自动测试全部通过，==但没有在生产环境验证==。
```

## 为什么会掉登录

前端判断「通行证快过期了没」时，用的是 UTC 时间；服务器写的是多伦多本地时间（UTC-5）。两边差 5 小时，于是前端以为通行证还有 4 小时，其实早过期了。

```flow 修复前的信息流：虚线是本该走、却一直没走到的那一步
((用户打开页面)) -> 前端读 token -> {快过期了吗?}
{快过期了吗?} -> 继续用旧 token! : 以为还有 4 小时
{快过期了吗?} ..> 去刷新 token : 本该走这条
继续用旧 token! -> 服务器拒绝 -> 用户被踢出
```

## 改了什么

```compare
### 之前
- 过期时间按字符串解析，默认当成 UTC
- 服务器返回的时间没有时区信息
---
### 之后
- 服务器返回带时区的 ISO 8601 时间
- 前端统一用 `Date.parse` 转成时间戳再比较
```

```steps
1. [x] **定位原因** 加日志对比前后端时间，发现差 5 小时
2. [x] **改服务器** `auth/session.py` 返回带时区的时间
3. [x] **改前端** `useSession.ts` 用时间戳比较，不再手动解析
4. [~] **补测试** 加了 3 个单元测试，还差一个跨时区的集成测试
5. [ ] **生产验证** 需要你部署后观察 1–2 小时
```

## 完整例子二：开工前的计划

```markdown
---
title: 头像上传加尺寸限制的计划
kind: plan
subtitle: 用户传 20MB 的原图把存储和页面都拖慢了
---

```tldr
打算在上传接口收到文件后、存进对象存储之前加一步检查和压缩：超过 **5MB** 或长边超过 **2048 像素** 的图在服务器端缩一下再存。只改 `api/upload.py` 和一个新的工具函数，前端不用动。==需要你决定：超限的图是直接拒绝，还是帮用户自动压缩？我倾向自动压缩。==
```

## 我理解的问题

现在上传接口拿到文件就原样存进 [[对象存储|像 S3 那样按「桶 / 文件名」存文件的云服务，按存量和流量收费]]，页面显示头像时也是直接加载原图。有人传了 20MB 的照片，头像列表页一次要加载几百 MB。

```flow 现在的流程：高亮的是没有任何检查的那一步
((用户选图)) -> 前端 POST /upload -> 原样存进对象存储! -> 列表页加载原图
```

## 打算分几步

```steps
1. [ ] **加检查** 在 `api/upload.py` 里读文件头拿到尺寸和大小，超限的走下一步
2. [ ] **加压缩** 新建 `utils/image.py`，用 Pillow 把长边缩到 2048、质量 85 存成 JPEG
3. [ ] **补测试** 三张图：正常、超大、不是图片的文件
4. [ ] **汇报** 给你前后文件大小的对比
```

## 会动到哪里

```kv
改动文件: `api/upload.py`
新增: `utils/image.py`、`tests/test_upload_image.py`
不动的: 前端、数据库结构、已经存进去的旧头像
依赖: Pillow（项目里已经有）
```

## 需要你决定的

```compare
### 自动压缩（我倾向）
- 用户无感，传什么都能成
- 代价：服务器多花 0.2–0.5 秒处理一张图
---
### 直接拒绝
- 实现最简单，不耗服务器
- 代价：用户要自己先缩图，很多人不会
```

```callout warn 一个风险
已经存进去的 20MB 旧头像不会自动变小。如果列表页现在就很慢，需要另开一个任务批量处理旧图。
```
```

## 常见的写坏的方式

| 写坏了 | 为什么不好 | 改成 |
|---|---|---|
| 开头先讲背景，结论在最后 | 读者要读完才知道成没成 | tldr 放第一块 |
| 「存在时区偏差导致鉴权失效」 | 全是术语，没有画面 | 「前后端差了 5 小时，前端以为还能用 4 小时」 |
| 「## 问题分析 / ## 解决方案 / ## 总结」 | 这是报告模板，不是读者的问题 | 「## 为什么会掉登录 / ## 改了什么 / ## 还没做的」 |
| 图上五个框全是名词，箭头没字 | 看不出机制，只是把目录画了一遍 | 箭头写上「做什么」，高亮出问题的那一步 |
| 「测试通过」 | 哪些测试、什么环境、没覆盖什么？ | 数字 + 环境 + 没覆盖的 |
| 把没做的事藏在最后一句 | 用户会错过，之后出问题怪你 | 单独 `callout warn`，tldr 里也点一句 |
| 1500 字、四张图 | 没人会读完 | 主干 300–600 字，细节进 `details` |
